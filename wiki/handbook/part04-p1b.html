Chapter 2PMK-ch02-

The map: two crates, three kinds of thread

The one structural picture the rest of the book assumes

MD Editor is a Cargo workspace with exactly two members. Almost every question of the form “where does this belong?” is answered by which of the two it is, and by which thread it is allowed to run on. Learn this chapter properly and the other thirty-one become local details.

2.1 The two crates

md-editor-core — the headless engine
Owns the disk and the database. Vault traversal, atomic writes, the SQLite schema, the full-text index, the wikilink graph, the PDFium worker thread, the cross-reference resolver, and the study tracker's persistence. It has no idea a window exists. All 56 of its tests run in a container with no display server.
md-editor-native — the desktop interface
Owns the screen. The Iced application loop, the custom markdown editor widget, the PDF page widget and its overlays, design tokens, motion, the command palette. It reaches the engine only through thread-safe methods on a shared Arc<AppState>, or through async tasks.

The dependency arrow points one way: native depends on core, and core must never learn about native. Three rules make that concrete, and they are the first three things a reviewer will check:

  1. No circular dependency. md-editor-core never depends on md-editor-native.
  2. No UI in core. The core crate must not take a dependency on a GUI or text-shaping toolkit — not iced, not winit, not ratex-render.
  3. Pure FFI containment. pdfium-render is reachable only through core/src/pdf.rs, and exactly one Pdfium binding may exist per process.

2.2 Three kinds of thread

Threading is where a desktop app is won or lost. MD Editor has three execution contexts and a strict rule about each.

  1. The UI main thread — the Iced event loop. Window events, typing, clicks, layout, drawing. It never blocks on disk or on PDF work.
  2. The Tokio async runtime — background work dispatched as iced::Task: autosave writes, vault indexing, FTS queries, PDF page renders, and syntax highlighting for large documents. Results come back as ordinary Message values.
  3. One dedicated PDFium worker thread — spawned by PdfRenderer::new(). Because pdfium-render keeps its bindings in a process-global cell, all PDF work is serialized onto this single thread. It is fed by two std::sync::mpsc channels: a priority channel for the page the reader is actually looking at, and a standard channel for everything else.
Trap The PDFium worker cannot interrupt an operation already in flight. Priority only decides what runs next. If you add a worker command that takes half a second — say, extracting text for a whole 500-page document in one go — every page render queues behind it and the reader watches a blank page. Chapter 21 shows the chunking pattern that exists precisely to avoid this.
Check yourself

You want to add “export the current note to HTML”. Which crate, and which thread?

Answer: the conversion itself is pure text-to-text with no GUI dependency, so it belongs in md-editor-core where it can be unit-tested headlessly. The file write goes through the existing atomic-write path in core/src/vault.rs. The native side contributes a menu entry and an iced::Task so the work runs on Tokio rather than on the UI thread — even though it is fast, because “it is fast” is how every stall starts.

Chapter 3PMK-ch03-

Your first hour

Build it, run it, and learn where the code actually is

Everything in this chapter is meant to be typed, not read. If a command fails, the fix is almost always in the prerequisites list — this is a project with a C compiler and a downloaded native library in its build path, and both can bite on a fresh machine.

3.1 Prerequisites

  • Rust — stable 1.85 or newer, because the workspace is on the 2024 edition.
  • A C compiler — gcc or clang. rusqlite compiles a bundled SQLite from source, so there is no system SQLite to install and no version skew to debug.
  • Network access, once — core/build_pdfium.rs downloads a prebuilt PDFium for your platform on the first build and caches it under target/pdfium/.
  • A desktop session — only to run the app. Tests do not need one.
Debian / Ubuntu
sudo apt update
sudo apt install -y build-essential pkg-config libxkbcommon-dev libfontconfig1-dev
sudo apt install -y libwayland-dev libx11-dev   # windowing
Arch
sudo pacman -S --needed base-devel pkgconf libxkbcommon fontconfig

3.2 The commands you will use every day

cargo fmt --check            # formatting — must be clean
cargo check --workspace      # fast typecheck
cargo test --workspace       # 158 tests: 56 core + 102 native
cargo clippy --workspace     # see the warning below
cargo run                    # launch a debug build
cargo build --release        # optimized binary
Trap cargo fmt --check and cargo test --workspace pass cleanly on main. Clippy does not. The tree carries 34 warnings (2 in core, 32 in native), mostly too_many_arguments, redundant_guard, and if_same_then_else, so -D warnings fails on a fresh checkout. Treat 34 as the baseline: compare the count before and after your change and fix anything your code adds. Do not open a pull request that raises it, and do not be alarmed when it is not zero.

The first build is slow — SQLite compiles from source and PDFium downloads — and every build after that is normal. The binary lands at target/release/md-editor (target\release\md-editor.exe on Windows) with the PDFium shared library copied beside it. It accepts a single path argument, which is how the Linux desktop entry hands it a file:

./target/release/md-editor ~/vault/Summary.md

3.3 Where the code actually is

The repository has 49 Rust files and about 26,000 lines. That distribution is very uneven, and knowing the shape of it is worth more than memorising the tree.

3.4 A first walk through the tree

Read these seven files, in this order, before you try to change anything. Skim; do not study. The goal is to have seen the names once.

#FileWhy it is on the list
1native/src/messages.rs The complete event vocabulary of the application in one enum. Reading it is the fastest way to learn what the program can be asked to do.
2native/src/main.rs Short. CLI arguments, window geometry restore, the Linux desktop entry, and the call that starts the Iced application.
3core/src/lib.rs Ten lines. Tells you exactly which modules the engine has.
4core/src/state.rs The AppState struct, the whole SQL schema, and the database path logic. Chapters 5–7.
5core/src/vault.rs Find write_file and read it twice. Chapter 8 is about those forty lines.
6native/src/theme.rs Every colour, size, spacing step and radius the UI is allowed to use. Small, and it will stop you writing a hardcoded 12.0 in your first pull request.
7native/src/app.rs — the update signature and the subscription function only Do not read all 4,344 lines. Read the shape: a match over Message, returning Task<Message>. Chapter 11.
Try it

Run the test suite and read its output rather than just its exit code:

cargo test --workspace 2>&1 | grep -E "^test |test result"

158 test names is a surprisingly good table of contents for a codebase. Names like write_file_never_leaves_a_truncated_file and blank_pages_reserve_space_in_total_height tell you what the authors were afraid of, which is usually the most useful thing to know about a program.

3.5 Optional: desktop integration on Linux

Linux builds are portable by default and integration is explicitly opt-in:

./target/release/md-editor --install      # or --install-desktop
./target/release/md-editor --uninstall    # or --uninstall-desktop

--install writes ~/.local/share/applications/md-editor.desktop, installs the icon at seven sizes under ~/.local/share/icons/hicolor/, and refreshes the desktop and icon caches where those tools exist. Both flags exit non-zero with a message on other platforms. The whole round-trip has a test — tests::test_linux_desktop_installation_roundtrip — which runs against a temporary $HOME, so it is safe on your machine.

Chapter 4PMK-ch04-

The language of this codebase

Twenty words you need, and the journey of one keystroke that uses all of them

Every codebase has private vocabulary, and misreading one word costs an hour. Here are the terms this one uses, roughly in the order you will meet them.

4.1 Vocabulary

TermWhat it means here
VaultThe open folder. Not a container, not a database — a directory you chose with a folder picker. All paths in the app are relative to its root.
Path jailingCanonicalising a path and refusing it if it does not lie strictly inside the vault root. resolve_vault_path_checked() in vault.rs.
Atomic writeWrite to a sibling temp file, fsync, rename over the target. A reader sees the whole old file or the whole new one. Chapter 8.
SidecarData about a file, stored outside it. Every PDF highlight is a sidecar record in SQLite.
document_idSHA-256 of a PDF's first 1 MiB plus its length. The identity a highlight is attached to. Deliberately excludes mtime. Chapter 22.
RopeThe ropey::Rope data structure behind DocBuffer. Makes inserts and line lookups cheap on large files.
Transaction (editor)A group of edit operations plus their inverses, so undo is a replay rather than a snapshot. Not a database transaction.
Undo runSeveral consecutive keystrokes coalesced into one undo step, so Ctrl+Z takes back a word. Chapter 13.
Retained bufferA parked DocBuffer — with undo stack, cursor and scroll — kept in an LRU registry of 32 when you navigate away from a note.
Conceal / revealHiding markdown syntax markers when the cursor is elsewhere and showing them when it is on the line. The whole “hybrid preview” idea. Chapter 14.
StyledSpanA run of characters with style, carrying both the raw text and an optional display_text. Concealing sets display_text = Some("").
Fenwick / HeightTreeA binary indexed tree over per-line visual heights. Turns “which line is at y?” from O(N) into O(log N). Chapter 15.
CullingDrawing only the lines inside the viewport. The draw pass must never iterate the whole document. Chapter 17.
GenerationA monotonically increasing id stamped on async work. A result whose generation no longer matches is discarded. Used for both highlighting and PDF rendering. Chapter 23.
Pending setThe set of in-flight requests of one kind (pending_pages, pending_links, pending_text). Cleaned up before the generation check, always.
Priority channelThe second mpsc channel into the PDFium worker, drained before each standard command, keeping only the newest request. Chapter 18.
Page slotThe fixed outer rectangle every PDF page occupies while scrolling, whether or not its bitmap has arrived. Chapter 24.
Synthetic TOCAn outline recovered from a PDF that has no embedded bookmarks, and marked as recovered in the UI. Chapter 20.
Reference linkA recognised in-prose mention like “Figure 1.1” turned into a clickable target, but only when the label matches exactly one target. Chapter 21.
Design tokenA named constant in theme.rs or motion.rs. Views are not allowed to use anything else. Chapter 26.
SubscriptionAn Iced stream of events the app opts into — and, in this codebase, one it opts out of the moment it has nothing to do. Chapter 12.

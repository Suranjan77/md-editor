The build system and PDFium

A native library that is downloaded at compile time and looked up at run time

PDFium is a large C++ library from Chromium. Building it from source is out of the question for a project this size, so core/build_pdfium.rs fetches a prebuilt binary, and bind_pdfium finds it again at run time. Two separate mechanisms, and most “PDFs don't work” reports are one of them.

PlatformArchitecturesSlugLibrary
Linuxx86_64 / aarch64linux-x64 / linux-arm64libpdfium.so
Windowsx86_64 / aarch64win-x64 / win-arm64pdfium.dll
macOSx86_64 / aarch64mac-x64 / mac-arm64libpdfium.dylib
Try it For a reproducible, verified build, set both variables: 
PDFIUM_RELEASE=chromium/6996 PDFIUM_SHA256=<hex digest> cargo build --release
Leaving them unset is fine for local development and is not fine for a release you are asking other people to run.

29.1 Continuous integration

.github/workflows/windows-build.yml — named for its original scope, it now covers the whole release pipeline. It runs on pushes to main, on v* tags, and on manual dispatch, with three jobs:

JobRunnerProduces
build-windowswindows-latest cargo build --release, then a package of md-editor.exe plus resources/pdfium.dll (downloaded separately from bblanchon/pdfium-binaries), zipped as md-editor-windows-x64.zip
build-linuxubuntu-latest the same layout using the libpdfium.so the build script already placed in target/release/, as both .tar.gz (which keeps the executable bit) and .zip
publish-releaseubuntu-latest downloads both artifacts and publishes a GitHub Release — v* tags are final, everything else publishes as latest and is marked pre-release
Trap CI does not run cargo test, cargo fmt --check, or cargo clippy. It builds and packages. Everything in Chapter 30 is the contributor's responsibility before opening a pull request — a green checkmark on your PR means “it compiled on two runners”, nothing more.

Give a first build on either runner extra time: rusqlite's bundled SQLite compiles from source and the PDFium archive downloads, both exactly once per cache.

30.1 Property suites: the editor's invariants

The editor's geometry is pinned by invariants rather than by examples alone. renderer/properties.rs generates documents from a seed — every block and inline kind, pathological nesting, CRLF, widths from 40 to 1400 px — using the generator it shares with the highlighter's suite (editor/test_docs.rs). A failing case is shrunk line by line and reported with its seed and a minimal document.

RENDER_PROPERTY_CASES=3000 cargo test -p md-editor-native properties   # before a renderer change lands

HIGHLIGHT_PROPERTY_CASES=3000 cargo test -p md-editor-native highlight
Why invariants An example test checks the document its author thought of. A generator writes thousands its author did not — a kerned pair at a row break, a checkbox beside an equation in a 40 px column — and the shrinker turns the one that fails into something a person can read. The height tree's floating-point drift (Chapter 15) was found this way. I12 is Chapter 17's culling rule made executable: it fails the moment a draw pass touches a line outside the viewport.

30.2 Three opt-in tools

Three renderer tests are marked #[ignore], so cargo test skips them. Each is a tool you run on purpose.

The render transcript harness

editor/render_snapshot_tests.rs drives the Editor widget purely through its Widget API — layout, draw, update, mouse interaction — against a document that exercises every block and inline kind, at three widths. It records every quad, text run and image drawn, every message published, clipboard writes and mouse-cursor shapes, into a plain-text transcript. Drawing goes to a recording renderer that borrows the real renderer's text measurement, so no window or GPU is needed.

RENDER_SNAPSHOT=/tmp/render.txt RENDER_SNAPSHOT_WRITE=1 \
  cargo test -p md-editor-native render_snapshot -- --ignored   # before the change: a baseline
RENDER_SNAPSHOT=/tmp/render.txt \
  cargo test -p md-editor-native render_snapshot -- --ignored   # after: compare
diff /tmp/render.txt /tmp/render.txt.actual | less
  • For a refactor, the comparison must pass. That is how splitting renderer.rs into renderer/ was verified to change nothing.
  • For a visual fix, the diff should contain the draw calls you meant to change, and nothing else.

The transcript is tens of megabytes and pins current behaviour, known bugs included, so keep it out of the repository.

Render previews

editor/render_preview.rs renders sample scenes to PNG through iced's tiny-skia software renderer — a caret mid-paragraph and after a checkbox, selections across wrapped rows, across lines and across a table, an equation and an image, a caret in equation source, a wide unfocused view — so rendering can be looked at without opening a window. It uses only the widget's public API, so the same file dropped into an older checkout renders a before-and-after pair.

RENDER_PREVIEW_DIR=/tmp/previews cargo test -p md-editor-native render_preview -- --ignored

The timing report

Prints what frames cost on a 37,000-line document — the table in Chapter 16. Run it in a release build; debug numbers mean nothing.

30.3 Where a new test goes

  • A bug fix in the markdown parser, undo grouping, or auto-pairing needs a regression test in native/src/editor/buffer.rs or editor/highlight.rs. A highlighter change must keep the incremental-equals-fresh property passing.
  • A rendering, caret or hit-testing bug in the editor needs a test in renderer/tests.rs, written against the draw calls and messages the widget produces rather than its internals, and seen failing before the fix. When the bug breaks a general rule, strengthen the matching invariant in renderer/properties.rs too, and run it at RENDER_PROPERTY_CASES=3000 before landing.
  • A change to wikilink parsing or resolution must be validated against core/src/massive_tests.rs.
  • A change to the reference resolver's output for the same input must bump references::RESOLVER_VERSION.
  • A change to PDF scroll or page geometry needs coverage in the page-slot tests in native/src/app.rs.
  • New core functionality belongs behind a headless test. If it cannot be tested without a window, it probably belongs in md-editor-native — that sentence is a design check as much as a testing rule.
Try it Break something on purpose and watch which test catches it. Change UNDO_COALESCE_WINDOW to 0 and run cargo test -p md-editor-native; then put it back and change the atomic write to a plain fs::write and run cargo test -p md-editor-core. Ten minutes, and you will remember which suite owns what for the rest of the project.

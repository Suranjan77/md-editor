Chapter 26PMK-ch26-

Tokens and motion

Six sizes, seven spacings, three radii, one curve — and the reason the list is short

Everything the chrome draws — sidebar, toolbar, panels, modals, tracker — takes its colour, size, spacing and radius from native/src/theme.rs. The module's own comment records why: before the scales existed the app had eleven distinct font sizes and seventeen distinct spacing values.

Why it is like this Eleven font sizes is the visual noise that reads as “unpolished” without ever being nameable. Nobody looks at a screen and thinks “that label is 13px and this one is 14px”; they think “this feels amateur”. A short scale removes the decision and the defect at once, and it makes review mechanical: a hardcoded number in a view module is wrong on sight, with no taste required.

Document typography — heading sizes and code or math scale inside a note — is a separate concern owned by the markdown renderer. Do not import theme.rs sizes into highlight.rs.

26.1 Motion

Before native/src/motion.rs the app had no motion at all: panels appeared and vanished between one frame and the next. Nothing is missing from a snapshot of an instant UI — it just feels abrupt, because the eye gets no continuity between the two states.

Motion holds an iced::Animation<bool> mirroring each visibility flag — sidebar, toc, backlinks, toast, palette — plus two things worth noticing:

  • now: Instant, the timestamp the current frame is drawn for. view reads this rather than calling Instant::now() itself, so every animation in a frame is sampled at the same moment. Without it, panels drift out of step within a single frame.
  • toast_text: String, retained after ui.toast clears — so the toast has something to draw while it fades out. An animation that outlives its data needs somewhere to keep it.

The booleans themselves stay where they live (sidebar visibility on the vault state, TOC on the editor pane); Motion only tracks how far each has travelled.

Chapter 27PMK-ch27-

The command palette and the fuzzy scorer

Making a command and a file comparable on one numeric scale

Ctrl+P opens a palette that searches commands and vault files together. That is only possible if both can be scored on the same scale — which is what native/src/fuzzy.rs is for.

native/src/fuzzy.rs
pub fn score(haystack: &str, query: &str) -> Option<i32>
pub fn score_path(path: &str, query: &str) -> Option<i32>

score walks the query left to right, advancing through the haystack to each next matching character, case-insensitively. None means the query does not appear in order at all — characters must be in order, but need not be adjacent, which is what makes initials work.

RuleEffect
Base+10 per matched character
Word start+18 when the character is at index 0 or follows a boundary — space / \ - _ . ( [
CamelCase+10 for an uppercase letter inside a word (mutually exclusive with the word-start bonus)
Adjacency+12 when it directly follows the previous match, rewarding runs
Distance penalty-min(gap, 8) for characters skipped since the previous match
Length normalization-(haystack.len() / 12) overall, preferring the tighter of two otherwise-equal matches

27.2 Ranking and interleaving

  • With an empty query the palette lists commands only — a menu of what the app can do. Files would just be an arbitrary slice of the vault.
  • With a query, commands are scored with fuzzy::score and files with fuzzy::score_path, then interleaved by relevance rather than split into fixed sections.
  • Directories are never offered as results.
  • The list is capped at MAX_RESULTS = 40 — past that the answer is a longer query, not more scrolling.
  • ↑/↓ move the highlighted row, Enter activates it, Escape closes. Changing the query resets the highlight to the first row, since keeping the old index would leave it on an unrelated result.

The palette's ranking is covered by eight unit tests, including that Enter activates exactly the highlighted row and that result_count matches what is rendered — the two properties a keyboard-driven list can silently get wrong.

Chapter 28PMK-ch28-

The study tracker

A timer, a log, and a curriculum the app knows nothing about

The tracker is the most self-contained feature in the app: three tables, one settings key, six tabs, and a deliberate refusal to model any particular subject.

28.1 Storage

WhereWhat
tracker_sessionsone row per logged interval, whether timed or entered by hand: id, date, hours, activity_type, phase, notes
tracker_kvthe checkbox and status state of the curriculum — project statuses (proj_<id>), gate ticks (gate_<id>_<n>), reading ticks (read_<section>_<n>). Written through tracker::set_kv, an upsert.
tracker_activitycreated by the schema, available for an activity feed; the current UI does not write to it.
settings['tracker_config']the curriculum itself, as JSON. It lives in settings rather than tracker_kv because it is one document, not a set of flags, and it is only accepted after parse_config validates it.
Note get_sessions skips a malformed row and logs it. Silently dropping study history would hide corruption — and a tracker whose totals quietly shrink is worse than one that complains.

28.2 The timer, and what it refuses to be

One button. Start records Instant::now() and toasts “Study timer started”. Stop computes elapsed.as_secs_f32() / 3600.0, floors it at 0.01 hours so a very short session still records something, and saves a StudySession immediately — date from chrono::Local::now() as "%Y-%m-%d %H:%M", activity_type = "Study", phase = "Focus", no notes.

There is no pause, no pomodoro cycle, and no post-stop dialog. To record an activity type or notes you use the Log tab's manual entry, which takes a date, an hours value and free text.

Why it is like this A dialog after every session is a tax on the behaviour the feature is trying to encourage. Saving immediately with defaults means the worst case is a row with a generic label — recoverable — rather than a session you abandoned because you did not want to fill in a form.

28.3 The configurable curriculum

Four collections, and the tracker understands nothing beyond their shape:

{
  "PHASES":   [{ "id": "1A", "title": "Mathematics", "year": "Year 1", "months": "Months 1-4" }],
  "PROJECTS": [{ "id": "1.1", "phase": "1A", "name": "SVD from scratch" }],
  "GATES":    [{ "id": "1A", "title": "Gate 1A - Mathematics",
                 "items": ["Derive SVD from eigendecomposition"] }],
  "READING":  [{ "section": "Textbooks - Mathematics",
                 "items": [{ "priority": "critical", "title": "Linear Algebra Done Right" }] }]
}

Out of the box it is seeded with a concrete four-year roadmap toward research in efficient machine learning — 17 phases (1A Mathematics through 4C Original Research), 20 projects, 6 checkpoint gates, and a reading list. That is a starting point, not a structure. The Config tab replaces it wholesale, and a language course, a thesis, or a certification path fits the same four collections exactly as well.

TrackerConfigSave runs parse_config first, which requires at least one phase and at least one project. An invalid document is rejected rather than saved, and a stored config that fails to parse falls back to the built-in default — so a bad edit costs you the edit, never the app.

Two lifecycle details: TrackerState::new loads sessions and key-values once at startup and validates the stored config before adopting it; opening the panel (TrackerToggle) reloads from disk, so an external change is picked up. Side effects that belong to the global UI are emitted as Message::ShowToast tasks rather than reaching back into the shell — the tracker never touches another pane's state, which is the sub-state rule from Chapter 11 in practice.

Note Gates are a self-assessment checklist, not an enforcement mechanism. Nothing in the app blocks progress on an unticked gate, and nothing should — the tracker's job is to show you where you are, not to hold a door shut.

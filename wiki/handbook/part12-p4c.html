Chapter 23PMK-ch23-

Generations, pending sets, and the stranded page

The bug this subsystem keeps trying to have, and the three-line shape that prevents it

If you read one chapter of Part IV twice, make it this one. Everything here is about asynchronous results arriving after the world has moved on, and the failure mode is a page that shows a loading state for ever.

23.1 The state involved

PdfPane (native/src/pdf_pane.rs) carries three in-flight request sets and one counter:

FieldMeaning
pending_pagespage images currently requested
pending_linkslink metadata currently requested
pending_texttext geometry currently requested; bounded by text_lru to 12 pages
render_generationbumped on a document change, a zoom change, or a navigation — so results from before the change can be recognised as stale

A pending set is not an optimisation. It is what stops the app requesting the same page fifty times while the first request is still in flight, so a page is scheduled only when the image is missing and the page is not already pending.

23.2 The invariant

native/src/app.rs — the shape every async PDF handler must have
Message::PdfRendered(generation, page, img) => {
    self.pdf.pending_pages.remove(&page);          // 1. always clean up first

    if generation != self.pdf.render_generation {  // 2. then discard if stale
        return Task::none();
    }

    // 3. only now touch the cache
}

The same shape applies to PdfRenderFailed, PdfPageLinksLoaded and PdfPageTextLoaded. Swap steps 1 and 2 — the ordering a normal person would write, because “ignore stale results” feels like the first thing to do — and you get Figure 23.1.

The corollary is just as important: any code path that increments render_generation must also clear the in-flight state belonging to the previous generation — pending_pages.clear() and pending_links.clear() — and a document change additionally clears page_links, pages, dimensions and page_sizes.

23.3 The deliberate exception

Why it is like this

PdfReferencesLoaded is gated on document_id, never on render_generation. References are a document-level artifact, and the chunked scan routinely outlives the fit-to-width zoom change that bumps the generation when a document opens.

Generation-gating them silently dropped every reference on first open. The tell was diagnostic gold: a reopened PDF worked — because it took the synchronous cache path — while a fresh one did not. PdfTocLoaded is gated on the document path for exactly the same reason.

Check yourself

You add “extract the annotations layer” as a new async PDF result. What are the two questions to answer before writing the handler?

Answer: (1) Which pending set does it belong to, and is it removed first? (2) Is this a per-render artifact (gate on render_generation) or a document-level one (gate on document_id)? Getting question 2 wrong is the references bug again; getting question 1 wrong is the stranded page again.

Chapter 24PMK-ch24-

Stable page slots

Why a rendered page must not change the space it occupies

A continuous PDF viewer has to answer “what is the scroll offset of page 300?” before page 300 has been rendered — and it has to give the same answer afterwards. Getting that wrong produces a bug that only appears deep in long documents, which is the worst kind.

24.1 The mechanism

Every page's unscaled size is loaded once with page_sizes(path) when the PDF opens — far cheaper than rendering, and available long before most pages enter the render queue. One of them (normally page 1) becomes placeholder_page_size. Then:

slot = (placeholder_width * zoom, placeholder_height * zoom)

Every page occupies that same outer slot while scrolling — including pages whose bitmaps have already rendered. Rendered bitmap dimensions are cached for image data and link maths, but they never change scroll geometry.

Page-size metadata drives loading placeholder dimensions, pdf_page_offset(page), pdf_page_at_scroll(scroll_y), viewport range detection, and the fit-to-width calculation — one source of truth feeding five consumers.

24.2 Rendering, supersampled

render_pdf_page() renders only the page image; it never extracts links. The PDFium render scale is supersampled relative to the displayed zoom — factoring in ui.scale_factor, the OS display scale — so a narrow split-view page stays sharp on HiDPI and fractional-scale displays without over-rendering on a 1× screen.

Trap Cached dimensions remain logical display dimensions, not raw bitmap dimensions. That distinction is what keeps link hit-testing and placeholder maths working in PDF-space/display-space geometry. Store the supersampled bitmap size there and every click lands in the wrong place on a HiDPI screen — and nowhere else, so you will not reproduce it.

On a successful PdfRendered: remove the page from pending_pages; discard if the generation is stale; store the handle in pages and (width, height) in dimensions; schedule low-priority link and text extraction for that page; and if the page is the active navigation target, compute the scroll offset and issue the programmatic scroll. A failure returns PdfRenderFailed rather than being swallowed by a generic tick.

24.3 Navigation and scrolling

TOC clicks, internal link clicks and PDF search-result clicks all funnel through navigate_pdf_page(page):

  1. clamp and store current_page;
  2. clear pending_pages and pending_links;
  3. increment render_generation;
  4. store toc_target_page;
  5. schedule link loading if the target page is already cached, otherwise request it through render_pdf_page_direct() — the priority channel;
  6. compute the target offset from the same stable slot geometry the view uses;
  7. set programmatic_scroll = true and issue scroll_to.

Scrolling then behaves differently depending on who caused it. User scrolling updates scroll_y, estimates the current page from y + viewport_height * 0.33, clears pending work if the page jump was large, and schedules viewport pages. Programmatic scrolling is acknowledged by the first matching PdfScrolled, which suppresses normal viewport scheduling for that event and schedules only a small range around the target.

Why it is like this Without that suppression, one TOC click would schedule the target page, its neighbours, the whole viewport and link extraction, all at once — on a single-threaded worker. The jump would be slower than scrolling there by hand.

The viewport window itself is deliberately generous but bounded:

first = page_at(scroll_y - estimated_page_height)
last  = page_at(scroll_y + viewport_height + estimated_page_height)
range = (first - 2) ..= (last + 2)

Search navigation is the one exception to the page-top model: navigate_pdf_search_to_index() computes the offset from the active match rectangle, priority-renders the match page, schedules a small nearby range, and scrolls the match into view. It deliberately leaves toc_target_page unset, because the render-completion page-top scroll would otherwise override the match-precise offset.

Chapter 25PMK-ch25-

From highlight to note and back

The pdf:// deep link, and the loop it closes

This is the feature the whole PDF subsystem exists to support: select a passage in a paper, attach it to a note, and be able to walk the connection in both directions afterwards.

25.1 What gets written

Selecting text and choosing Link to Note opens a searchable in-app vault picker (views/link_note_picker.rs): pick an existing note, or pick a folder and type a new note name. native/src/pdf_notes.rs generates the markdown.

---
type: pdf-note
source_pdf: papers/Introduction to Algorithms.pdf
---

# Divide and conquer

## Page 42

> A divide-and-conquer algorithm breaks down a problem into two or more
> sub-problems of the same or related type...

[Open highlight in PDF](pdf://papers/Introduction to Algorithms.pdf?page=42&annotation=abcdef123456)

### Notes

This definition connects to [[Lecture 3 Notes]].

Six behaviours are worth knowing before you touch this file:

  • A new note gets type: pdf-note / source_pdf: frontmatter and an # H1 title derived from its filename (shared pdf note.md becomes # Shared pdf note).
  • Reusing an existing note appends another ## Page N section after a --- rule, rather than overwriting the file.
  • Re-linking the same highlight is idempotent — append_linked_pdf_note_section checks for the generated link and returns the file unchanged if it is already there.
  • Page numbers in the heading and the link are 1-based, while page_index is 0-based. Off-by-one bugs here are visible to the user, so the convention is worth internalising.
  • The link target is the vault-relative PDF path, not the document_id; relative paths are resolved against the note's own location.
  • The visible markdown carries no debug identifiers. The annotation id lives only inside the pdf:// link, where it is needed for exact navigation.
Trap Linked-note writes must append to an existing note unless the exact highlight link is already present. Overwriting is the obvious implementation and it silently destroys a user's notes on the second highlight they link to the same file. The idempotency check exists for the third one.

Chapter 13PMK-ch13-

DocBuffer, transactions, and word-sized undo

Why one Ctrl+Z takes back a word, and how a quote knows it is an apostrophe

DocBuffer is the text model: a ropey::Rope, a cursor, a selection, and an undo stack of transactions. Everything the editor can do to text is an EditorCommand applied through DocBuffer::execute().

native/src/editor/buffer.rs
pub enum EditorCommand {
    InsertText(String), DeleteSelection, DeleteBackward, DeleteForward,
    MoveCursor { movement: Movement, extend: bool },
    SetCursor { line: usize, col: usize, affinity: Affinity },
    SetSelection { anchor_line: usize, anchor_col: usize,
                   focus_line: usize, focus_col: usize, affinity: Affinity },
    SelectAll, ToggleCheckbox { line: usize },
    FormatBold, FormatItalic, FormatInlineCode, InsertLink,
    TypePaired(char), Undo, Redo,
}

execute() returns a CommandResult { text_changed, projection_changed, media_changed }, so the shell knows whether to re-parse the document, refresh the image and math caches, or merely move the caret. Three booleans, and they save an enormous amount of unnecessary work: moving the cursor changes the projection but not the text, so nothing is re-highlighted.

Why a rope A String is one contiguous allocation. Inserting a character in the middle of a 2 MB note memmoves the tail — every keystroke. ropey stores the text as a tree of chunks, so an insert touches one chunk, and it also gives O(log n) conversion between character offsets and line/column, which the editor asks for constantly.

13.1 Human-sized undo

A keystroke-by-keystroke undo stack is technically correct and miserable to use: taking back one sentence costs a dozen presses. commit_transaction therefore coalesces consecutive edits into one undo step.

const UNDO_COALESCE_WINDOW: Duration = Duration::from_millis(300);

can_coalesce(prev, next) merges only when every one of these holds:

  • the new transaction is a single operation;
  • it is the same kind as the previous one — an insert continues inserts, a delete continues deletes;
  • neither text contains a newline, so a run always breaks at a line boundary at the latest;
  • the new character lands exactly where the previous one ended, so a cursor jump breaks the run;
  • there was no active selection, so a selection-replacing edit is always its own step;
  • less than UNDO_COALESCE_WINDOW has passed, so a deliberate pause starts a new step.
native/src/editor/buffer.rs — the insert arm, lightly trimmed
(EditOp::Insert { char_offset: prev_at, text: prev_text },
 EditOp::Insert { char_offset: next_at, text: next_text }) => {
    next_text.chars().count() == 1
        && !next_text.contains('\n')
        && !prev_text.contains('\n')
        // The new character lands exactly where the previous one ended.
        && *next_at == prev_at + prev_text.chars().count()
}

13.2 Smart auto-pairing

Bracket and quote characters route through TypePaired; everything else inserts verbatim. Four behaviours, and the fourth is the one people notice when it is missing.

BehaviourRule
BracketsPAIRS = [('(', ')'), ('[', ']'), ('{', '}')]. Typing an opener inserts the pair and places the cursor between them.
Selection wrappingWith a selection active, typing (, [, {, ", ' or ` wraps the selection rather than replacing it.
Skip-overTyping a closer that already sits at the cursor steps over it instead of inserting a duplicate. Same for an identical quote directly ahead.
Contraction preservation", ' and ` pair by default — but a quote typed immediately after an alphanumeric character is left single, so don't, it's and users' do not sprout stray closers.

There is a regression test for exactly this. Any new text-scanning code in this file should use chars() and character indices for the same reason.

13.4 Grapheme clusters and caret affinity

Columns in DocBuffer are char offsets, but the caret never stops inside what a person would call one character. ←/→ step, and Backspace/Delete remove, one extended grapheme cluster (unicode-segmentation): 👩‍💻 is three chars joined by a zero-width joiner, and one step. A line break — \r\n included — is one stop. set_cursor, set_selection and vertical movement snap a column that lands inside a cluster back to its start.

Wrapping creates a second ambiguity. Where a line breaks between rows, one column is both the end of the earlier row and the start of the later one, and the caret has to be drawn at exactly one of them.

Because the affinity describes one particular placement of the caret, the buffer owns it: DocBuffer::cursor_affinity is set only by SetCursor and SetSelection, and reset by every other change. It cannot outlive the placement it describes.

Why it is like this If the widget kept its own copy of the affinity, an edit or an undo that moved the caret would leave that copy describing a placement that no longer exists, and the caret would be drawn at the end of the wrong row. Keeping every caret fact — position, selection, affinity — in DocBuffer, with no copy on the widget, makes that bug unrepresentable. Chapter 32 states it as a rule.
Check yourself

You type hello, wait two seconds, type world, then press Ctrl+Z twice. What is on screen after each press?

Answer: hello, then empty. The two-second pause exceeded UNDO_COALESCE_WINDOW, so there are exactly two runs.

Chapter 14PMK-ch14-

Hybrid preview and incremental highlighting

One data structure that holds both the source and what you see — kept in step with the text a line at a time

There is no preview mode and no edit mode. The document renders as formatted typography, and the line your cursor is on shows its raw markdown in place. The whole trick is that a span carries two strings.

14.1 The data structures

native/src/editor/highlight.rs
pub struct StyledLine {

    pub is_code_block: bool,
    pub is_math_block: bool,
    pub code_block_lang: Option<String>,

pub struct StyledSpan {
    pub text: String,                  // the raw markdown source for this span
    pub display_text: Option<String>,  // what preview shows; Some("") hides a marker
    pub color: Color,
    pub bold: bool, pub italic: bool, pub font_size: f32,
    pub is_code: bool,
    pub is_link: bool, pub link_target: Option<String>,
    pub is_heading: bool, pub heading_level: u8,
    pub is_checkbox: bool, pub is_checked: bool,
    pub is_list_marker: bool,          // bullet, number or checkbox: wrapped rows hang past it
    pub is_rule: bool,
    pub is_image: bool, pub image_path: Option<String>, pub image_alt: Option<String>,
    pub is_math: bool,
    pub is_syntax: bool,               // this span is a marker like ** or $ or ```
    pub id: Option<String>,
}

text always holds the exact source. Nothing is lost by concealing — the renderer simply chooses display_text instead. That is why editing works normally on a concealed line: the characters are still there, they are just drawn as nothing. Which spans on the active line actually reveal is decided per span, for the caret's column, in renderer/spans.rs — which is why the caret's column is part of the line cache key in Chapter 16.

14.2 Incremental highlighting

A line's highlighting is a pure function of two things: its own text, and the state it is entered in — whether a code fence, a math block or a table is open above it.

native/src/editor/highlight.rs
pub struct LineState { code: Option<CodeState>, in_math: bool, in_table: bool }
struct CodeState { lang: Option<String>, syntax: Option<(ParseState, HighlightState)> }

Highlighted keeps, for every line, its text, the LineState it was entered in, and how it opens, continues or closes blocks. update(text) then does the least work that can possibly be correct:

  1. find the common prefix and suffix of the old and new line texts;
  2. re-highlight from the first changed line, starting in that line's recorded entry state;
  3. stop as soon as it reaches the kept suffix in the same state that line was entered in before — from there on nothing can differ — and splice the new lines in;
  4. run decorate over the whole document: block numbering, math-block concealment and caption numbering, which depend on neighbours rather than on one line.

Highlighting therefore runs synchronously on every edit — measured at about 0.03 ms per keystroke on a 700-line note and 0.34 ms at 7,000 lines. There is no debounce, no placeholder lines and no background task, so the painted lines always match the buffer. Each update also takes a new, process-wide unique revision(), which names that set of lines; Chapter 16 uses it to skip layout entirely on frames where nothing changed.

Why it is like this An asynchronous highlighter needs a generation id so that a slow parse of old text cannot overwrite newer text — the pattern Chapter 23 describes for PDF renders. But even with the id, the lines on screen lag the buffer for a moment after each keystroke, and a click in that moment is hit-tested against lines that no longer describe the text: it lands on the wrong line. Making the work small enough to do synchronously removes the lag, the id, and that bug together.
Note Two properties are pinned by tests. Fenced code coloured by syntect preserves the full source text character for character — a highlighter that quietly drops a character is a data-loss bug wearing a cosmetic disguise. And incremental highlighting equals highlighting from scratch, checked through seeded random edit scripts (HIGHLIGHT_PROPERTY_CASES=N raises the case count). A new markdown rule must keep both passing.
Check yourself

A 500-line note contains no code. You type ``` at the start of line 10. How many lines are re-highlighted? Then you replace line 20 with a closing ``` — how many now? Then you type one ordinary letter on line 30?

Answer: 491, then 481, then 1. Opening the fence changes the entry state of every later line, so the walk never meets a line in its old state and runs to the end. Closing it on line 20 changes the entry state of line 21 onwards back again — every later line differs from a moment ago. The ordinary letter changes no state, so the walk stops at line 31.

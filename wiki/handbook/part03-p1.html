What you are looking at

The product, and the four decisions everything else follows from

MD Editor is a desktop workspace for people who read papers and write notes about them: a markdown editor on one side, a PDF reader on the other, a search index across both, and a study timer underneath. It is written in Rust, it runs entirely on your machine, and it stores your work as ordinary files in an ordinary folder.

That description is short enough to fit on a landing page, and it hides everything interesting. What makes this codebase worth reading is not the feature list — plenty of programs edit markdown — but the four commitments the author made early and then refused to bend, because every non-obvious piece of code in the repository is downstream of one of them.

1.1 The four pillars

Local-first, and no proprietary format

A vault is a directory. You open one with a native folder picker and MD Editor indexes what it finds: markdown (.md, .markdown), PDFs, and images (.jpeg, .jpg, .png, .svg, .webp, .avif — the list in core/src/vault.rs, which is not quite the list the README prints; see Appendix B). Nothing is imported, converted, or moved. Your notes stay readable by cat, editable by Vim, and syncable by Git, rsync, or Syncthing.

There is no account, no licence key, and no telemetry. The only network access anywhere in the project is the build script fetching PDFium, and that happens once, at compile time (Chapter 29).

Zero-configuration portability

Everything that is not your content — settings, window size, per-document scroll and cursor positions, PDF highlights, cached PDF text, resolved cross-references, study history — lives in a single SQLite file called md_editor_settings.sqlite. By default that file sits beside the executable, so the whole application is one folder you can drop on a USB stick. Chapter 7 covers what happens when that directory is read-only.

Durability and continuity

Typing must survive a crash, a power cut, and a window closed in a hurry. The app therefore treats disk as the source of truth and commits aggressively: an autosave fires 400 ms after you stop typing, every write is atomic, and navigating away from a note flushes it first — refusing to navigate if the write fails. Chapters 8 and 31 are entirely about this.

Non-destructive sidecar annotations

A paper you are reading is reference material, and the app treats it as immutable. Highlight a passage and MD Editor writes a row in SQLite — never a byte into your .pdf. This is the decision with the longest tail of consequences, and Figure 1.1 is the shape of it.

Why it is like this

Every one of these pillars costs something. Sidecar annotations mean your highlights do not open in Acrobat. Portability means the database is in a slightly unusual place. Aggressive autosave means the code has to be careful about writes in a way a “save when the user asks” editor never does.

They were chosen anyway because the failure they prevent is worse than the cost they impose: a research vault you cannot read without the tool that made it is a vault you will lose.

1.2 What it actually does, briefly

You will understand the code faster if you have used the program for ten minutes. The feature surface, in one pass:

AreaWhat a user getsWhere it lives
Markdown editing Hybrid live preview — formatted text that reveals its raw syntax on the line the cursor is on, with no mode switch. Inline and display LaTeX, images, tables that scroll on their own, task lists you click. native/src/editor/
Smart typing Auto-paired brackets and quotes that know what a contraction is, list continuation with ordered-list increment, and an undo that takes back a word rather than a character. native/src/editor/buffer.rs
Linking [[Wikilinks]] that resolve across subfolders by filename, and a backlinks panel that shows both notes and PDF highlights pointing at the open document. core/src/file_index.rs
PDF reading Continuous scroll, fit-to-width, a recovered table of contents when the file has no bookmarks, recognised cross-references (“see equation (3.14)”) you can right-click to preview. core/src/pdf.rs, references.rs
Study workflow Highlights in five cycling colours, quick notes, and “Link to Note”, which writes a markdown section quoting the passage with a pdf:// deep link back to the exact page. native/src/pdf_notes.rs
Search Three of them: in-note with regex and replace, PDF search with a loose-whitespace mode for phrases that wrap across lines, and a global FTS5 search covering notes and extracted PDF text together. core/src/vault.rs, native/src/search.rs
Tracker A timer, a session log, and a configurable curriculum of phases, projects, gates and reading lists. core/src/tracker.rs
Try it Before reading Chapter 2, build and run the app on a scratch folder with one markdown file and one PDF in it (Chapter 3 has the commands). Type a sentence, press Ctrl+Z once, and watch a whole word-run disappear rather than one character. That behaviour is Chapter 13, and it is much easier to read the code once you have felt the thing it produces.
Check yourself

You copy your vault folder to a new laptop but forget the application folder. What survives?

Answer: every note, PDF and image — and none of the highlights, study history, scroll positions or cached text, because those live in the settings database beside the executable, not in the vault. Whether that split is right is a genuine design question; Chapter 22 explains why the annotations were nevertheless not put inside the PDFs.

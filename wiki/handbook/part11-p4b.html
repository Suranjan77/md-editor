Chapter 21PMK-ch21-

Resolving “see equation (3.14)”

A pure resolver, one hard precision rule, and the chunking that keeps it from blocking renders

Papers reference their own equations, figures, tables and sections by number all the time, and almost never carry link annotations for those mentions. core/src/references.rs reads the extracted text and turns the mentions into clickable targets.

core/src/references.rs
pub fn resolve_references(pages: &[PdfPageText], toc: &[TocEntry]) -> Vec<ReferenceLink>

The resolver is pure: it reads already-extracted page text plus the outline, touches no PDFium, and is therefore Send, cheap (roughly 15–30 ms for a full textbook) and unit-testable without a window. That signature is a design statement — the hard part of this feature is a text problem, not a rendering one, so it is kept where it can be tested.

21.1 Two passes and one gate

Three precision rules were learned from a real corpus and are worth stating explicitly, because each one is a bug that was observed before it was fixed:

  • Reject bare four-or-more-digit parenthesised numbers. (2003) is a citation year, not equation 2003.
  • Capture dotted figure and table numbers — otherwise Figure 1.1 and Figure 1.2 collapse into one target called “1” and both become ambiguous.
  • Require a dotted section number. A bare chapter integer is too coarse to aim at.

21.2 Chunked scanning

References need the whole text layer. PDFium is single-threaded, and priority renders only drain between worker commands (Chapter 18) — so one monolithic full-document command would block page rendering for half a second or more. The native side therefore resolves references as a chunked background task:

  1. get_embedded_toc(path) for section targets — cheap, no text scan;
  2. extract text one page at a time with get_page_text(path, i), so queued priority page renders interleave between pages;
  3. if there were no embedded bookmarks, recover the outline from the text just collected with recover_toc_from_texts(&pages) — no second scan;
  4. run resolve_references(&pages, &toc) on the async thread.

For bookmark-less PDFs the full scan already happens for TOC recovery, so references are effectively free. For bookmarked PDFs the chunking is what keeps first-open rendering responsive.

21.3 Caching, versioning, and aiming the preview

Results are cached in pdf_references keyed by document_id, stored as (RESOLVER_VERSION, links). get_pdf_references discards entries whose version does not match the current resolver, so changing the algorithm invalidates stale results rather than serving them.

Trap Bump references::RESOLVER_VERSION whenever the resolver's output for the same input would change. It is currently 2. Forget it and every existing user keeps the old — now wrong — cached links for ever, while your machine, which has a fresh cache, looks perfect.

One more detail, and it is a nice example of caring about the actual reading experience: a caption sits beside its artwork, not on it. So scan_caption_callsites nudges the preview target off the caption — figures up (caption-below convention), tables down (caption-above) — by CAPTION_PREVIEW_SHIFT = 110.0 points, about a third of the 300 pt preview window, so the figure fills the frame instead of being clipped.

Recognised references are drawn with a subtle accent underline. Those rects set OverlayRect.thin, which bypasses the minimum-size clamp that keeps highlight rectangles legibly tall, letting the underline render as a true hairline.

Try it Two examples exist for working on this code: 
cargo run --example dump_refs  -- path/to/paper.pdf   # resolved references with surrounding text
cargo run --example bench_refs -- path/to/paper.pdf   # text-scan cost per document

dump_refs is the precision spot-check: run it on a paper you know and read the surrounding text of every link it claims. A single wrong link is worth more attention than ten missing ones, because a wrong link makes the reader stop trusting the underlines entirely.

Chapter 22PMK-ch22-

Sidecar annotations and document identity

What a highlight is attached to, when it survives, and how you find out it drifted

Highlighting text never modifies the .pdf on disk. That raises an immediate question: if the annotation is not in the file, what is it attached to?

22.1 The identity function

core/src/pdf.rs
pub fn compute_provisional_id(path: &Path) -> Result<(String, u64, Option<i64>), String>

The document_id is the SHA-256 of the first 1 MiB of the file plus its length, in hex. Two deliberate choices are buried in that sentence:

  • A bounded prefix, not the whole file. Hashing 1 MiB keeps opening a 500-page PDF cheap. Adding the length makes truncation or extension detectable without reading the rest.
  • mtime is excluded on purpose. Including it would orphan every annotation whenever the file was copied, restored from a backup, or re-downloaded. The mtime is still returned and recorded in pdf_documents for bookkeeping — it just is not part of identity.

22.2 The annotation record

core/src/pdf.rs
pub struct PdfAnnotation {
    pub id: String,
    pub document_id: String,
    pub page_index: u16,
    pub kind: PdfAnnotationKind,        // Highlight | Note
    pub color: PdfAnnotationColor,      // Yellow | Green | Blue | Pink | Orange
    pub selected_text: String,
    pub ranges: Vec<PdfTextRange>,      // character intervals on the page text layer
    pub rects: Vec<PdfRect>,            // bounding boxes in PDF points
    pub note: Option<String>,
    pub linked_note_path: Option<String>,
    pub markdown_anchor: Option<String>,
    pub created_at: i64,
    pub updated_at: i64,
}

Two fields are stored where one might do. ranges are character intervals on the text layer — the semantic anchor, used by the drift report. rects are geometry in PDF points — what gets drawn. Keeping both is what lets the app detect that a highlight has moved rather than silently drawing it in the wrong place.

Colour cycling. PdfAnnotationColor::next() advances Yellow → Green → Blue → Pink → Orange → Yellow, and PdfPane::next_highlight_color steps through it after each quick highlight, so successive highlights stay visually distinct without the reader choosing a colour every time. The explicit Message::PdfCreateHighlight(color) path lets you pick one deliberately.

22.3 Text search, and the whitespace problem

core/src/pdf.rs
pub fn search_text(&self, path: &str, query: &str, regex: bool, match_case: bool)
    -> Result<Vec<PdfSearchMatch>, String>

The worker walks each page's text layer, builds the page string alongside a char_indices map back into PDFium's own character indices, finds matches (a compiled regex when regex is set, otherwise a literal), and converts each match into PdfRects via text_page.segments_subset.

Loose whitespace mode is a native-side convenience built on the same regex path (app.rs::search_pdf):

let pattern = query.split_whitespace()
    .map(regex::escape)
    .collect::<Vec<_>>()
    .join(r"\s+");

Three lines that make PDF search actually usable on papers: a phrase still matches when the extracted text puts a line break or a run of spaces between the words, which is exactly what happens when a sentence wraps across a PDF line or column.

Note It does not rejoin words hyphenated across a line break. A word split as algo- / rithm still has to be searched in halves. That is a known limit, stated in the release notes rather than hidden.

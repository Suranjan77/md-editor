Reading the enum for clues

Three details in that list are worth noticing, because each is a design decision made visible:

EditorCommand and EditorCommandNoScroll — some edits should not move the viewport, and that is expressed as a separate message rather than a boolean parameter.

PdfRendered, PdfRenderFailed and PdfRenderSkipped — three distinct outcomes, so a failure is never silently indistinguishable from a deliberate skip (Chapter 23).

KeyboardShortcut(Shortcut) rather than one variant per binding — the indirection that lets the keyboard subscription and the command palette trigger the same handler (Chapter 27).

Starter tasks, graded

Six ways in, roughly in order of difficulty

Each of these is a real, self-contained piece of work in this codebase. For each one: the files you will touch, the tests you should add, and the rules from Chapter 32 that apply. None of them is busywork — they are all things the program would genuinely be better for.

1 · Add a command to the palette warm-up

Something small and useful: Copy File Path, which puts the active document's vault-relative path on the clipboard and raises a toast.

Touchmessages.rs (a Shortcut variant), views/command_palette.rs (the registry), app.rs (the handler)
Testextend the palette ranking tests so the new command is findable by its initials
Rulesone registry, one code path; the toast uses the existing Message::ShowToast
Why it teachesyou will touch the message enum, the router, a sub-state and a view in one change — the whole shape of Chapter 11 in twenty lines

2 · Decide what the image list should be judgement, small

Appendix B's trap: the wiki and README used to claim .gif and .bmp were supported and did not mention .svg or .avif. Those pages have been corrected to match IMAGE_EXTENSIONS — but the interesting half of the question is still open. The docs promised GIF and BMP for a reason; should the code deliver them, or was dropping them deliberate?

Touchcore/src/vault.rs — and, if you change it, wiki/User-Guide-and-Feature-Manual.md, wiki/Architecture-and-Philosophy.md and README.md in the same pull request
Testif you extend the list, a test that a file with each extension is indexed as an image — and check the renderer actually draws it before you promise it
Why it teachesthe documentation rule is not decoration, and “make the docs true” is only half a fix when the docs described something a user reasonably wanted

3 · Rejoin hyphenated words in PDF search small feature

Loose whitespace mode (Chapter 22) matches a phrase across a line break, but a word split as algo- / rithm still fails. Extend the generated pattern so an optional hyphen-plus-whitespace can appear inside a word.

Touchapp.rs::search_pdf
Testa core test over synthetic page text containing a hyphenated break
Watch outdo not break genuinely hyphenated words (state-of-the-art) and do not make the pattern quadratic; the constraint is precision, exactly as in Chapter 21

4 · Give tracker_activity a producer, or remove it judgement

The table is created by the schema and written by nothing (Chapter 28). Either wire an activity feed to it — session started, session saved, gate ticked — or make the case for dropping it. Both are legitimate; the work is in arguing for one.

Touchcore/src/tracker.rs, views/tracker.rs, and — if you remove it — apply_migrations() rather than the base DDL
Why it teachesChapter 6's migration rule, and the discipline of deciding whether unused code is a plan or a leftover

5 · Add a block type to the editor the four-call-site contract

A callout / admonition block (> [!note]) that draws a tinted background and a label. This is the task that teaches the layout system properly.

Touch, together(1) editor/highlight.rs — parse it, assign a block_id; (2) the layout pass — block-range tracking and height measurement including any spacer; (3) the draw pass — block backgrounds, clamped to the visible range; (4) hit testing
Testheight permutations in editor/renderer.rs, and a highlighter test that the source text is preserved character for character
RulesChapter 32 rule 3, all of it. If the new block's height depends on anything new, it goes into line_hash or resource_hash

6 · Make the FTS index incremental engine, hard

Today file_search is rebuilt wholesale when a vault opens (Chapter 10). On a very large vault that is the slowest part of opening. Update rows from the filesystem watcher instead, keeping the wholesale rebuild as a fallback.

Touchcore/src/vault.rs, app.rs's VaultFilesChanged handler
Testextend the FTS suite in core/src/massive_tests.rs: create, edit, rename, delete — and assert the index matches a full rebuild afterwards
Watch outthe current design's virtue is that the index cannot drift out of sync. Any incremental scheme has to be at least as trustworthy, or it needs a “rebuild index” command — which is a feature admitting a bug
RulesChapter 5's lock discipline: compute into a local, then lock, then assign
Whichever you pick Run the four pre-PR commands (Chapter 32.2), compare the clippy count before and after, and if your change touches saving, navigation, animation or the PDF pane, walk the relevant items in Chapter 33 — particularly the durability checks, which no automated test fully replaces.
Appendix EPMK-apE-

Where to go next

Five things to remember, and what to read when you forget the rest

If you remember only five things

  1. The engine is headless and the interface owns the screen. When you cannot decide where code goes, ask whether it can be tested without a window. That answer is almost always the right one.
  2. Slow work happens before the lock, never inside it. Compute into a local, then lock, then assign.
  3. Writes are atomic and navigation flushes first. Never replace the temp-file-and-rename protocol with a truncating write, and never navigate away from a failed save.
  4. The draw pass is proportional to the viewport, not the document. Everything in Chapters 15–17 exists to keep that true.
  5. Async results clean up before they are gated. Remove from the pending set, then check the generation — and gate document-level artifacts on the document, not the generation.

The habit worth copying

The most transferable thing in this repository is not the Fenwick tree or the priority channel. It is that almost every non-obvious decision carries its reasoning next to it — in a module comment, in a test name, in a wiki page. write_file_never_leaves_a_truncated_file is a better specification than three paragraphs of prose, and it fails loudly when someone stops believing it.

When you add something here, add the why with it. That is the practice this handbook is trying to hand on more than any particular fact inside it.

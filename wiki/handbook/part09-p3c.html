Chapter 15PMK-ch15-

The Fenwick height tree

Turning “which line is at this y?” from O(N) into O(log N)

In a document where every line is the same height, finding the line at a scroll position is a division. In this editor lines are not the same height — a heading is taller, an image line is much taller, a wrapped paragraph is taller still, and a line's height changes when a LaTeX bitmap arrives. So the editor keeps a spatial index.

15.1 The problem

Three questions get asked constantly, on every scroll and every draw:

  • How tall is the whole document? (for the scrollbar)
  • What is the y offset of line L? (to draw it)
  • Which line is at y? (for culling, and for every click)

Answering any of them by summing an array of heights is O(N) — and it happens per frame. On a 10,000-line document that is a stall you can feel.

15.2 The structure

native/src/editor/layout_tree.rs
pub struct HeightTree { tree: Vec<f32>, heights: Vec<f32> }

pub fn update_height(&mut self, idx: usize, new_height: f32); // O(log N)
pub fn prefix_sum(&self, idx: usize) -> f32;                  // O(log N)
pub fn find_line_at_y(&self, y: f32) -> usize;                // O(log N), binary lifting
pub fn get_height(&self, idx: usize) -> f32;                  // O(1)

A Fenwick tree (binary indexed tree) stores partial sums in a flat array. Cell i holds the sum of a range whose length is the lowest set bit of i. That single rule gives you prefix sums and point updates in logarithmic time with no pointers, no rebalancing, and one allocation.

15.3 What it buys

OperationBrute-force scanHeightTree
Total document heightO(N)O(log N) — one prefix_sum(n)
Y offset of line LO(L)O(log N)
Line at a Y coordinateO(N)O(log N), binary lifting on prefix sums
Update one line's heightO(1)O(log N)

Note the one row where the tree is worse: updating a single height. That is the trade, and it is obviously worth it — updates happen when a line is remeasured, queries happen several times per frame.

Two implementation details in update_height are worth copying:

  • It short-circuits when the delta is below 1e-5, so remeasuring a line to the same height costs nothing at all. Given that most remeasures produce the identical number, this removes most of the update traffic.
  • Each stored height is not just the text height: it is the sum of an optional block-top spacer (24px before an inactive code or table block), the measured line height, and a table scrollbar gutter where applicable. The tree's unit is “vertical space this line occupies”, not “font metrics”.
Try it Open native/src/editor/layout_tree.rs and read the tests at the bottom. They assert two things: that prefix_sum agrees with a brute-force sum for random height vectors, and that find_line_at_y is monotonic and correct at boundaries. That is exactly the right pair of properties for a structure like this — an oracle test and an edge test — and it is a good template if you ever add a similar index.
Check yourself

An image finishes loading and line 4 grows from 60 to 300 pixels. What has to happen?

Answer: update_height(4, 300), which adds the delta of 240 to O(log N) cells — cells 5, 6 and 8 in our example. Every subsequent prefix_sum and find_line_at_y is then correct, with no rebuild. The separate question of how the editor knew to remeasure that line at all is Chapter 16.

Chapter 16PMK-ch16-

Measure once: the line cache

Text shaping is the expensive part, so the answer is remembered — carefully

Measuring a line means shaping glyphs: resolving the font, applying metrics, and doing word wrap at the current width. It is the dominant cost of a layout pass, and in debug builds it is brutally slow. LineHeightCache memoizes it per line.

native/src/editor/layout_cache.rs
pub struct LineHeightCache {
    pub hash: u64,               // line_hash ^ resource_hash
    pub is_editing: bool,
    pub active_col: Option<usize>,
    pub height: f32,
    pub valid: bool,
}

A cached height is reused only when all four of valid, the combined hash, is_editing and active_col match. Miss any one and the line is remeasured.

Trap If you add state that affects a line's height, add it to line_hash or resource_hash. Otherwise you have silently made the layout pass do a full shaping call for every line on every frame — or, worse, kept a stale height forever. Neither failure produces an error message; the first shows up as “debug builds crawl” and the second as “the layout is subtly wrong sometimes”.
Chapter 17PMK-ch17-

The draw pass

The one rule that keeps a 10,000-line note scrolling: draw only what is visible

Editor implements iced::advanced::Widget — not canvas::Program, because it needs its own layout, hit testing and event handling, which the canvas abstraction does not provide. Content is capped at MAX_CONTENT_WIDTH = 880.0 so prose keeps a readable measure in a wide window.

17.1 Two passes with different budgets

Layout walks every line once — but every line is a cache hit unless something about it actually changed (Chapter 16), and the walk maintains block_ranges for O(1) block lookups. Total height is TOP_PAD + prefix_sum(n) + 80.0.

Draw must never walk the document. It walks the viewport:

  1. find_line_at_y(viewport.y - bounds.y - TOP_PAD) gives visible_start; the same call at the viewport's bottom edge gives visible_end;
  2. block backgrounds are built only for blocks intersecting that range;
  3. lines are drawn starting at prefix_sum(visible_start) and stop once the y position passes the viewport bottom.

17.2 Four more things the widget does

Inline and display LaTeX

$...$ and $$...$$ are rendered by ratex-render into bitmaps, cached on app.rs by (tex, scale_factor) and delivered back through Message::MathRendered. Display math is centred with its own background padding; inline math sits on the text baseline. Because the render is asynchronous, its arrival changes resource_hash and the affected lines are remeasured — the loop closed in Chapter 16.

Wide blocks scroll independently

Tables, code blocks and wide equations neither wrap awkwardly nor stretch the layout. Each block keeps its own horizontal scroll offset, clamped to its own content width, so a wide table scrolls sideways under the mouse wheel while vertical document scrolling is unaffected.

Hit testing and visual movement

  • Click and drag y positions map to line indices through HeightTree.
  • Horizontal wheel and scrollbar interaction resolve the target block via block_ranges plus prefix sums.
  • Visual up/down computes the current visual y from the tree, hit-tests the target y, and preserves a desired_visual_x across consecutive arrow presses — so the caret does not drift left while moving through a run of short lines.
  • Horizontal placement still walks the visible spans, because column mapping depends on inline wrapping, font metrics, math and image widths, and hidden markers. To make that affordable the renderer caches single-character width measurements by character, font and size.

17.3 The maintenance contract

Why it is like this

The five rules below are stated in the module and repeated in the contributor guidelines, and they are really one rule seen from five angles: the pieces of the layout system only work together.

  • Keep parsing in highlight.rs; do not add markdown rules to the renderer.
  • Keep height and invalidation logic in layout_tree.rs and layout_cache.rs.
  • Keep the draw pass proportional to visible content, never to document length.
  • When adding media that can affect layout height, include its dimensions in resource_hash.
  • When adding a block type, update block-range tracking, height measurement, draw metadata and hit testing together — they are one contract split across four call sites.
Check yourself

You add a “callout” block type that draws a coloured background and an icon. Which four places change?

Answer: (1) highlight.rs, to parse it and assign a block_id; (2) the layout pass's block-range tracking and height measurement, including any spacer the block adds; (3) the draw pass's block-background construction, clamped to the visible range; (4) hit testing, so clicking inside the callout maps to the right line and column. Miss the fourth and clicks land one line off — which is exactly the kind of bug that gets reported as “the editor feels weird”.

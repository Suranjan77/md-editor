Chapter 15PMK-ch15-

The Fenwick height tree

Turning “which line is at this y?” from O(N) into O(log N)

In a document where every line is the same height, finding the line at a scroll position is a division. In this editor lines are not the same height — a heading is taller, an image line is much taller, a wrapped paragraph is taller still, and a line's height changes when a LaTeX bitmap arrives. So the editor keeps a spatial index.

15.1 The problem

Three questions get asked constantly, on every scroll and every draw:

  • How tall is the whole document? (for the scrollbar)
  • What is the y offset of line L? (to draw it)
  • Which line is at y? (for culling, and for every click)

Answering any of them by summing an array of heights is O(N) — and it happens per frame. On a 10,000-line document that is a stall you can feel.

15.2 The structure

native/src/editor/layout_tree.rs
pub struct HeightTree { tree: Vec<i64>, heights: Vec<i64> }   // fixed point, UNITS_PER_PX = 256

pub fn update_height(&mut self, idx: usize, new_height: f32); // O(log N)
pub fn prefix_sum(&self, idx: usize) -> f32;                  // O(log N)
pub fn find_line_at_y(&self, y: f32) -> usize;                // O(log N), binary lifting
pub fn get_height(&self, idx: usize) -> f32;                  // O(1)

A Fenwick tree (binary indexed tree) stores partial sums in a flat array. Cell i holds the sum of a range whose length is the lowest set bit of i. That single rule gives you prefix sums and point updates in logarithmic time with no pointers, no rebalancing, and one allocation.

15.3 What it buys

OperationBrute-force scanHeightTree
Total document heightO(N)O(log N) — one prefix_sum(n)
Y offset of line LO(L)O(log N)
Line at a Y coordinateO(N)O(log N), binary lifting on prefix sums
Update one line's heightO(1)O(log N)

Note the one row where the tree is worse: updating a single height. That is the trade, and it is obviously worth it — updates happen when a line is remeasured, queries happen several times per frame.

Three implementation details are worth copying:

  • Heights are stored as fixed-point integers — UNITS_PER_PX = 256, so every sum is exact however many lines are added and removed. The public API still speaks f32 pixels; only the storage is integral.
  • update_height short-circuits when the delta is zero, so remeasuring a line to the same height costs nothing at all. Most remeasures produce the identical number, so this removes most of the update traffic — and in integer units “identical” is exact.
  • Each stored height is a line's whole extent, not its text height: its collapsed top margin, a caption band on the first line of a code block or table (BLOCK_CAPTION_HEIGHT = 24), its body, and a scrollbar gutter under a table's last row (HORIZONTAL_SCROLLBAR_GUTTER = 16). The tree's unit is “vertical space this line occupies”, not “font metrics”.
Trap — and the bug that made it one An earlier version of the tree stored f32 heights. Floating-point addition is not exact, and a Fenwick cell is adjusted by every update beneath it, so over a long editing session rounding error accumulated in the cells until prefix_sum no longer agreed with the heights it was built from — and hit testing picked the wrong line. A property test found it. Integers do not drift.
Try it Open native/src/editor/layout_tree.rs and read the tests at the bottom. They assert two things: that prefix_sum agrees exactly with a brute-force sum for random height vectors, and that find_line_at_y is monotonic and correct at boundaries. That is exactly the right pair of properties for a structure like this — an oracle test and an edge test — and it is a good template if you ever add a similar index. The renderer's property suite adds a third one level up: height_tree_agrees_with_line_visual_y checks the tree against an uncached model of the whole layout (Chapter 30).
Check yourself

An image finishes loading and line 4 grows from 60 to 300 pixels. What has to happen?

Answer: update_height(4, 300), which adds the delta of 240 to O(log N) cells — cells 5, 6 and 8 in our example. Every subsequent prefix_sum and find_line_at_y is then correct, with no rebuild. The separate question of how the editor knew to remeasure that line at all is Chapter 16.

Chapter 16PMK-ch16-

Measure once: the line cache and the layout key

Text shaping is the expensive part, so the answer is remembered — and when nothing changed, not even asked for

Measuring a line means shaping glyphs: resolving the font, applying metrics, and breaking rows at the current width. It is the dominant cost of layout. The editor avoids it at two levels: LineHeightCache remembers each line's body height, and LayoutKey skips the layout pass altogether on a frame whose inputs have not changed.

16.1 The line cache

native/src/editor/layout_cache.rs
pub struct LineHeightCache {
    pub hash: u64,               // line_hash ^ resource_hash
    pub is_editing: bool,
    pub active_col: Option<usize>,
    pub math_head: bool,         // whether the line carries its math block's height
    pub height: f32,             // the body alone
    pub valid: bool,
}

The cache holds a line's body — its rows of text, its image, its equation — and nothing that depends on its neighbours. Margins do (Chapter 17), so they are never cached: a cheap walk recomputes them on every layout. A cached body is reused only when valid, the combined hash, is_editing, active_col and math_head all match. Miss any one and the line is remeasured.

Why block_id is not in the hash block_id numbers blocks from the top of the document, so inserting a line above a block renumbers it — and every block below — without changing anything a line's own height depends on. With block_id in the hash, pressing Enter near the top of a long note would remeasure every block beneath it.

16.2 The layout key: skipping layout entirely

The cache makes a layout walk cheap, but a walk over 37,000 lines is still 37,000 lookups — and Iced rebuilds the view on every scroll and animation frame. So the widget remembers what its last layout was computed from:

native/src/editor/renderer/mod.rs
struct LayoutKey {
    revision: u64,          // the app's revision of the lines, images and equations
    lines: usize,
    width: u32,             // bits of the width laid out at
    focused: bool,
    cursor: (usize, usize),
}

The revision is a promise from the app. EditorPane::layout_revision() hashes Highlighted::revision (Chapter 14), the number of images and equations in its caches, and the display scale, and hands the result to the widget through Editor::layout_revision(u64). Images and equations are only ever added, or all dropped when the scale changes, so those counts identify them. While the revision, the width, focus and the caret are all the same as last time, layout is skipped entirely.

Read the table from the bottom. The frames that matter most — scrolling and animation, which change nothing a layout depends on — cost 47 nanoseconds instead of fifteen milliseconds, which at 60 fps would have been almost the entire frame budget. The numbers come from an ignored test you can run yourself (Chapter 30).

One related detail: Widget::size() reports the editor's height as Shrink. The real height is only known once the document is laid out at the width the widget actually gets, so nothing ever measures the document at a guessed width.

Trap If you add state that affects a line's height, it has to reach both levels. Add it to line_hash or resource_hash, and make sure changing it changes EditorPane::layout_revision or LayoutKey. Miss the first and a stale height is reused; miss the second and the widget never even looks — it paints the previous layout. Neither failure produces an error message; both show up as “the layout is subtly wrong sometimes”.
Check yourself

A LaTeX bitmap for line 900 arrives while you are scrolling. Which of the two levels notices, and how?

Answer: both, in order. The math cache on EditorPane gains an entry, so layout_revision changes and the LayoutKey no longer matches — the widget walks the lines again. During that walk line 900's resource_hash now includes the bitmap's dimensions, so its cache entry misses and that one body is remeasured; every other line is a hit. The next scroll frame matches the new key and skips layout again.

Chapter 17PMK-ch17-

The widget: rhythm, rows, and the draw pass

One place computes each fact, everything else asks — and the draw pass only asks about what is visible

Editor implements iced::advanced::Widget — not canvas::Program, because it needs its own layout, hit testing and event handling, which the canvas abstraction does not provide. Content is capped at MAX_CONTENT_WIDTH = 880.0 so prose keeps a readable measure in a wide window.

The widget used to be one 4,400-line renderer.rs. It is now native/src/editor/renderer/, one module per concern, and it rests on four principles worth reading before any of its code:

  1. One source of truth per fact. Row breaks, baselines, margins, scroll extents and the caret's position are each computed in exactly one place; everything else asks.
  2. Layout is a pure function of the lines, the width, the caret and the loaded resources. Every cache is checked against a cold recomputation by a property test.
  3. Invariants before code. Behaviour is pinned by seeded property suites (Chapter 30) as well as by examples.
  4. Exact over estimated. Positions come from the shaper and the font's own metrics; motion comes from closed-form springs (Chapter 26), not frame-by-frame integration.

17.2 Typographic rhythm

Every vertical measure in a document is a multiple of GRID = 4px, so baselines in different blocks share one grid. The numbers live in renderer/metrics.rs:

  • Row height — row_height(font_size) interpolates line height from 1.6 at the 17px body size down to 1.2 at 34px, because large type needs less leading, and snaps to the grid. A body row is 28px; code rows are row_height(15).
  • Blank lines are paragraph gaps, PARAGRAPH_GAP = 20px — still tall enough to hold the caret.
  • Margins — each line asks for space above and below by kind: headings from HEADING_MARGINS (48/16px for # down to 24/8px), and code blocks, tables, block math, images, rules and quote runs BLOCK_MARGIN = 16px.

The whole collapsed margin is realised above the lower line, so a block's box starts exactly at its content, and the painters read margins from State::line_margins rather than deriving them again.

17.3 Inline layout: the Flow

Every line that is not a code line, a rendered table row or rendered block math is laid out by Flow::build in renderer/flow.rs, and that is the only place rows are broken. Line heights, painting, the caret, selection and search highlights, and click and hover hit testing all read the same Flow — so the caret always sits on the painted text, and a click lands where it is drawn.

  • Shaping — prose is shaped with Shaping::Advanced (kerning, ligatures); monospace keeps Shaping::Basic so columns line up as typed. Each word is shaped once per font and size, and the x of every character boundary inside it comes from the shaper's own grapheme_position (measure.rs::word_offsets), so the caret sits exactly between kerned glyphs and never inside a cluster.
  • Breaking follows Unicode line-break opportunities (UAX #14, unicode-linebreak): between words, after hyphens and dashes, inside long URLs. Trailing whitespace hangs past the right edge; a word wider than a whole row breaks between grapheme clusters.
  • Hanging indents — wrapped rows of a list item, task or numbered item start under its text, not under its marker (the is_list_marker flag from Chapter 14).
  • Balanced headings — a wrapped heading nobody is editing is re-laid at the narrowest width that keeps the same number of rows (bisection, 14 steps), so its rows come out even instead of ragged. A heading being edited keeps greedy breaks, so text does not jump between rows while you type.
  • Row height and baselines — a row is as tall as the larger of row_height for its largest text and its content (plus INLINE_MATH_ROW_PADDING with an equation on it), snapped up to the grid. measure.rs::font_metrics reads ascent, descent and x-height from the face the shaper uses; every item on a row shares its baseline, and checkboxes and inline equations centre on the axis, half an x-height above it. Painted text snaps to device pixels.
  • Columns ⇄ x — caret(col, affinity) places a column; col_at(x, y) returns a column and an affinity. Past the end of a row that wraps it answers Upstream, so the caret stays on the clicked row (Figure 13.2).
Trap Never measure or break inline text outside flow.rs. A second wrapper — in a painter, a hit tester, a highlight — will agree with the first on most lines and disagree on a few: a kerned pair, a hyphen, a checkbox. Where they disagree the caret is drawn beside the text instead of in it, or a click selects the character next to the one under the pointer. Laying inline text out once is how the caret, clicks and painting were made to agree. If you need to know where text is, ask the line's Flow.

17.4 Two passes with different budgets

Layout — layout_lines in renderer/layout.rs — runs only when the LayoutKey changed (Chapter 16). It walks all lines, taking each body from LineHeightCache unless something about the line changed, recomputing margins, and filling the height tree and block_ranges. Total height is TOP_PAD + prefix_sum(n) + BOTTOM_PAD, 24 and 80 px.

Draw — renderer/draw/ — must never walk the document. It walks the viewport:

  1. find_line_at_y(viewport.y - bounds.y - TOP_PAD) gives visible_start; the same call at the viewport's bottom edge gives visible_end;
  2. measure_blocks() measures only blocks with a line in that range, and their chrome — cards, captions, language badges — is painted first;
  3. each visible line is laid out once into a LineBox, its Flow included, and every step below reads those boxes;
  4. the selection's pieces over text are painted under everything;
  5. each line gets its search highlights, then one painter chosen by kind — rule, code line, table row, block math, or flow — then the caret;
  6. the selection's pieces over tables, images and equations are painted in a layer of their own, and block scrollbars last.

17.5 The selection, and why it needs layers

A selection is painted as one continuous shape: a full-height band per visual row it touches, bridged across the space between lines wherever neighbouring bands overlap, with corners rounded only where they stick out. A selection that continues past the end of a line gets an 8 px tail there, standing for the selected line break, so selected blank lines stay visible.

Tables, images and equations are selected whole, and their bands are painted over them — an opaque table header or picture would hide a band beneath it — while bands over text go under it, where a translucent band on top would dim the glyphs. Doing that correctly depends on how renderers really paint.

Trap — layers, not clip rectangles

A renderer paints each layer's quads, then its images, then its text, whatever order they were drawn in. Anything that must appear over an image or text needs a later layer, not a later call.

Clipping has the same shape. Clip with a layer (renderer.with_layer), never with the clip rectangle passed to fill_text or draw_image: no iced backend clips an image to it, and a text clip rectangle inside the enclosing layer switches tiny-skia's clipping off. So wide code, tables and equations are painted inside a layer bounded by the block's viewport (draw/blocks.rs::block_clip), with their text drawn using the frame's viewport as its clip rectangle. The test recorder models both rules, so Call::paint_order and each call's clip show what a renderer really puts on screen.

17.6 Revealing the caret

Keeping the caret in view is a two-party problem. The widget knows exactly where the caret is drawn but cannot scroll the scrollable it sits in; the app can scroll, but cannot see where the caret is drawn. They meet halfway, and nothing is estimated — there is no per-keystroke centring and no guess at the editor's width.

  1. A command that should keep the caret visible calls EditorPane::request_reveal — Reveal::Nearest for typing and caret movement, Reveal::Center for search navigation, table-of-contents clicks and heading links. This bumps reveal_request; while a request is unanswered the stronger mode wins, so a jump that centres is not downgraded by the cursor move made on the way.
  2. On the next RedrawRequested — layout final, viewport known — the widget answers with a CaretView: the caret's top and bottom, the viewport's top and height, and its own height, all relative to the widget.
  3. app.rs::reveal_caret asks CaretView::viewport_top_for. Nearest scrolls only if the caret is within the comfort margin of an edge, and then only by the amount that restores the margin; Center puts it mid-view.
  4. The target is clamped to the scrollable range and reached with a Spring (SCROLL_STIFFNESS, Chapter 26), retargeted with its momentum if typing continues mid-glide. A wheel turn or click fires EditorScrollInterrupted and hands the page back (Chapter 12).

17.7 Three more things the widget does

Inline and display LaTeX

$...$ and $$...$$ are rendered by ratex-render into bitmaps, cached on EditorPane by TeX source for the current display scale — flushed and re-rendered when the scale changes — and delivered back through Message::MathRendered. Display math is centred with its own padding; inline math centres on the row's axis. Because the render is asynchronous, its arrival changes the layout revision and resource_hash, and the affected line is remeasured — the loop closed in Chapter 16.

Wide blocks scroll independently

Tables, code blocks and wide equations neither wrap awkwardly nor stretch the layout. Each block keeps its own horizontal scroll offset, clamped to its own content width — scroll.rs::scroll_extent is the one answer to how wide a block is and how much of it shows — so a wide table scrolls sideways under the mouse wheel while vertical document scrolling is unaffected. A code block scrolls by the least amount that keeps the caret CODE_CARET_MARGIN (24 px) inside its viewport, and an equation's number sits outside the equation's viewport, so a scrolled equation never runs under it.

Hit testing and visual movement

  • Click and drag y positions map to line indices through HeightTree, then to a column and affinity through the line's Flow. A drag keeps tracking the pointer outside the widget.
  • Horizontal wheel and scrollbar interaction resolve the target block via block_ranges plus prefix sums.
  • Visual up/down moves exactly one visual row, starting from the caret's own row — its affinity included — and keeps a desired_visual_x across consecutive presses, so the caret does not drift left while moving through a run of short lines.

17.8 The maintenance contract

Why it is like this

These rules are stated in the wiki and repeated in the contributor guidelines, and they are really one rule seen from several angles: each fact has one owner, and the pieces only work together.

  • Keep parsing in highlight.rs; do not add markdown rules to the renderer. A new rule must keep incremental highlighting equal to a fresh pass.
  • Never measure or break inline text outside flow.rs.
  • Caret facts — position, selection, affinity — live in DocBuffer. The widget keeps no copy.
  • Keep height and invalidation logic in layout_tree.rs, layout_cache.rs and renderer/layout.rs.
  • Put any size that layout, painting and hit testing must agree on in renderer/metrics.rs, never as a literal at one call site, and keep vertical sizes on the GRID.
  • Keep the draw pass proportional to visible content, never to document length.
  • Clip with layers, and remember that a layer paints its quads, then images, then text.
  • When adding media that can affect height, include its dimensions in resource_hash and make sure a change to it changes EditorPane::layout_revision.
  • When adding a block type, update block-range tracking, body height, margins, draw metadata, and hit testing and scrolling together — one contract split across five call sites.
Check yourself

You add a “callout” block type that draws a tinted background and a label. Which places change?

Answer: the parser, then the five call sites. First highlight.rs, to parse it and assign a block_id — keeping incremental-equals-fresh passing. Then (1) layout.rs::record_block_range; (2) layout.rs::line_body_height; (3) layout.rs::requested_margins, probably with BLOCK_MARGIN; (4) draw/blocks.rs::measure_blocks, for the card, clamped to the visible range; and (5) scroll.rs::scroll_extent, so clicks and scrolling inside the callout resolve to the right line and column. Miss the last and clicks land in the wrong place — exactly the kind of bug that gets reported as “the editor feels weird”. Finish with a behaviour test in renderer/tests.rs, seen failing first.

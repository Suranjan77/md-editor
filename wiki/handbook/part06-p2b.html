Chapter 8PMK-ch08-

The atomic save

Forty lines in vault.rs that decide whether the program is trustworthy

This is the most important function in the repository. If you read one thing carefully, read vault::write_file — and then read the four unit tests underneath it, which exist because every step below is load-bearing.

8.1 The problem

The naive save is fs::write(path, content). It opens the destination, truncates it to zero bytes, and writes. If the process dies in the middle — a crash, a kill -9, a power cut — the file on disk is now half a note. The old version is gone and the new one never arrived. For an application whose entire pitch is “your work is safe in plain files”, that is not an edge case; it is the thing being promised against.

Worse, this app saves constantly: 400 ms after you stop typing, on every navigation, and on window close. A rare failure mode multiplied by a very high write frequency is a common failure mode.

8.2 The protocol

In the order the code performs it:

  1. Canonicalize the destination. A symlinked note is written through to its target rather than replaced by a regular file.
  2. Create a sibling temp file — .<filename>.<uuid>.tmp, in the destination's own directory, so the final rename can never cross a filesystem boundary. The UUID means two concurrent saves cannot collide.
  3. Write the bytes, then copy the destination's permissions onto the temp file, so a note kept at 0600 does not come back world-readable.
  4. file.sync_all() — flush the contents to physical storage.
  5. fs::rename() — atomically replace the destination.
  6. sync_all() on the parent directory, best-effort, so the rename itself survives a power loss.

8.3 The tests that hold it in place

Four unit tests live in core/src/vault.rs and each maps to one property above. If you change this function, you will meet them:

  • content replacement leaves no .tmp files behind;
  • permissions are preserved;
  • a symlink is written through, not over;
  • write_file_never_leaves_a_truncated_file — the name is the specification.

8.4 Where saves are triggered from

Three call sites, with three different failure policies. The differences are deliberate.

TriggerPolicy on failure
Autosave — 400 ms after the last keystroke, polled every 100 ms Raise a toast the first time in a run of failures, keep the unsaved marker in the title, and restart the debounce. Toasting on every poll would be a strobe light.
Navigation — opening another note, an image, or a PDF Refuse to navigate. The view does not change and the error is surfaced. Walking away from work that could not be persisted is the one thing the app will not do.
Window close Best-effort, and it does not block the close. An app that refuses to quit because a write is failing is a worse outcome than losing the few hundred milliseconds autosave had not yet committed.
Why it is like this The close-window exception looks like an inconsistency and is actually the harder call. The reasoning is about what the user can do next: a refused navigation leaves them in the editor, where they can fix the problem. A refused quit leaves them with a window that will not close, which is a support ticket and a force-kill — and a force-kill loses strictly more.
Check yourself

Why must the temp file be a sibling of the destination, rather than in /tmp?

Answer: rename() is only atomic within a single filesystem. A temp file in /tmp is very likely on a different mount, so the “rename” would degrade into a copy-then-delete — which is exactly the non-atomic write the whole protocol exists to avoid, now with extra steps.

Chapter 9PMK-ch09-

Wikilinks and the backlink graph

One regex, a three-step resolver, and why incoming is stored rather than derived

A vault is a graph as well as a folder. core/src/file_index.rs is 403 lines that keep that graph correct while files are created, renamed, edited and deleted underneath it.

9.1 Parsing

core/src/file_index.rs
static WIKILINK_RE: LazyLock<Regex> =
    LazyLock::new(|| Regex::new(r"\[\[([^\]|]+)(?:\|[^\]]+)?\]\]").unwrap());

Compiled once, reused for every file in the vault. It matches both the bare form [[Note Name]] and the aliased form [[Note Name|Display Text]], and captures only the target — the alias affects display, never resolution.

Note LazyLock matters more than it looks. Compiling a regex is expensive; compiling it inside the per-file loop would make indexing a 2,000-note vault noticeably slower for no reason at all. If you add a pattern to this module, add it the same way.

9.2 Resolution

resolve_link(target, from_file) tries three things in order.

9.3 The bidirectional index

core/src/file_index.rs
pub struct FileIndex {
    pub outgoing: HashMap<PathBuf, HashSet<PathBuf>>, // file → files it links to
    pub incoming: HashMap<PathBuf, HashSet<PathBuf>>, // file → files that link to it
    vault_root: PathBuf,
    names: HashMap<String, BTreeSet<PathBuf>>,        // lowercased stem → candidates
}

incoming could be derived from outgoing on demand — scan every file's outgoing set looking for the one you care about. It is stored instead, because the Backlinks panel is drawn on every relevant redraw and a map lookup is free where a full scan is not.

Two functions maintain it:

  • rebuild() runs in two passes: register every filename first, then resolve links. This is not a style choice — a bare [[Name]] must be able to reach a file that appears later in the listing, or in a different subfolder. A single pass would resolve links against a half-built name map and produce different results depending on directory iteration order.
  • update_file() does the same incrementally for one edited file, and its first action is to remove that file's previous outgoing edges from every target's incoming set. Forget that and deleting a link from a note leaves a permanent phantom backlink.
Trap Anything you change here must survive core/src/massive_tests.rs, which fuzzes wikilink variants, graph topologies (stars, chains, cycles, disconnected islands) and a dynamic create/edit/delete workload. That suite exists because this exact code is easy to get subtly wrong and impossible to eyeball.
Chapter 10PMK-ch10-

Full-text search

One FTS5 table, one quoting rule, and backlinks that are not only wikilinks

Global search is a single SQL statement. The interesting parts are the quoting, and the fact that the index contains PDF text as well as markdown.

10.1 The query

core/src/vault.rs::search_vault
SELECT path, snippet(file_search, 1, '<b>', '</b>', '...', 15)
FROM file_search
WHERE content MATCH ?1
ORDER BY rank
LIMIT 100;

The query string is wrapped in double quotes before it reaches MATCH, with any embedded quotes doubled, so it is treated as an FTS5 phrase rather than as query syntax.

Why it is like this FTS5's MATCH takes a small query language: AND, OR, NEAR, prefix stars, column filters. Passing raw user input straight in means someone searching for NOT or a AND b gets an unexpected result — or a syntax error where they expected zero hits. Quoting turns the whole input into one literal phrase, which is what a search box in a notes app should mean.

Results carry the path and a highlighted snippet, ordered by FTS5's own rank, capped at 100. On the native side the query is debounced by SEARCH_DEBOUNCE = 200ms, so a ten-character query runs one scan rather than ten (Chapter 12).

10.2 One index, two kinds of document

file_search holds (path, content) rows for markdown notes and for text extracted from PDFs. That is the entire reason global search covers papers as well as notes, and it is why vault indexing (Chapter 5) has a phase 1b that runs PDFium.

The table is rebuilt wholesale, inside one transaction, whenever a vault is opened — not maintained incrementally. For vault sizes this app targets that is simpler and fast enough, and it means the index can never drift out of sync with the filesystem in a way that requires a “rebuild index” command.

10.3 Backlinks beyond markdown

get_mixed_backlinks(state, path) answers “what points at the thing I am looking at?”, and the answer depends on what that thing is.

Active documentWhat comes back
A markdown note MarkdownFile { path } — every note whose [[wikilink]] resolves to this one, straight from FileIndex::get_backlinks.
PdfAnnotation { document_path, annotation_id, page } — every sidecar highlight whose linked_note_path is this note, joined from pdf_annotations to pdf_documents. Activating one opens that PDF at the exact page and focuses the highlight.
A PDF MarkdownFile { path } — notes that wikilink to the PDF itself.
MarkdownFile { path } again, but carrying the highlight's selected_text as context — notes reached through this PDF's own annotations, so the panel can show which passage produced the link.
Note BacklinkTarget::PdfDocument { path } is defined in core/src/types.rs and rendered by views/backlinks.rs, but no query currently emits it. It is a wired-up variant with no producer — worth knowing before you spend an hour looking for the code path that creates one.
Check yourself

A user searches for 1.5" (with a quote character). What reaches SQLite?

Answer: "1.5""" — the whole thing wrapped in quotes with the embedded quote doubled, which FTS5 reads as the literal phrase 1.5". Without the doubling the quote would terminate the phrase early and the rest would be parsed as query syntax.

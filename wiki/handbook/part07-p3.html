Chapter 11PMK-ch11-

The shell: one loop, one router

The Elm architecture, and the rule that keeps app.rs from becoming everything

Iced is an Elm-architecture toolkit: state, a Message enum, an update that folds messages into state, and a view that renders state. MD Editor starts the application through Iced's function API rather than the older trait.

native/src/main.rs
iced::application(
    move || app::MdEditor::new_with_startup_file(startup_path.clone()),
    app::MdEditor::update,
    app::MdEditor::view,
)
.title(app::MdEditor::title)
.theme(|state: &app::MdEditor| state.theme())
.subscription(app::MdEditor::subscription)
.window(iced::window::Settings { size: restore_window_size(), icon, platform_specific, ..Default::default() })
.run()

11.1 The loop

Startup is short and worth knowing, because two of its steps are easy to be surprised by: read_startup_value("window_size") opens its own database connection before AppState exists — the window has to be sized before the app is constructed — and the restored size is parsed and clamped, falling back to 1200×800 on anything nonsensical.

11.2 Sub-states, and why active_path is not one of them

MdEditor is not one giant struct of fields; it composes seven domain sub-states, each owning its own data and the messages that touch only that data.

Sub-stateOwns
EditorPane
editor_state.rs		 The active DocBuffer, the highlighted lines and the generation id that discards stale background highlights, the autosave timestamp, scroll offset, TOC visibility, and the retained-buffer registry (MAX_RETAINED_BUFFERS = 32). Also defines the timing constants: HIGHLIGHT_DEBOUNCE = 80ms, AUTOSAVE_DEBOUNCE = 400ms, AUTOSAVE_POLL = 100ms, LARGE_DOC_LINE_THRESHOLD = 1_000, HUGE_DOC_LINE_THRESHOLD = 5_000.
VaultState
vault_state.rs		 Vault root, file entries, sidebar selection and folder expansion, the backlinks panel.
UiState
ui_state.rs		 Modals, the command palette and its highlighted row, the toast, split-view state and divider ratio, window size, and the display scale factor that drives PDF supersampling.
SearchState
search_state.rs		 Query and replacement text; the regex, match_case and PDF-only loose flags; vault and PDF results; and a memoized in-document match cache keyed by DocMatchKey so view never rescans the buffer. SEARCH_DEBOUNCE = 200ms.
TrackerState
tracker_state.rs		 Timer state, loaded sessions, tracker key-values, active tab, and the JSON config editor content.
PdfPane
pdf_pane.rs		 The PDF viewport, page caches, annotations, selection, and the render generation. Chapters 23–24.
Motion
motion.rs		 How far each animated panel has travelled, and the single Instant the current frame is sampled at. Chapter 26.

Three pieces of state deliberately stay on the shell itself: active_path (the current document, which the editor, search, and PDF pane all need), active_panel (which pane last received direct interaction, so split-view shortcuts route correctly), and showing_pdf.

Why it is like this The shell is also the only place that owns the shared Arc<AppState>. That is not incidental: it means a sub-state cannot reach into the engine even if someone wants it to, so “open a file” or “create a vault entry” can only be written in the one place that can also update every other pane afterwards. Restricting access is how the coupling stays visible.
Trap When you add a message, the question to answer first is “does this touch fields of exactly one sub-state?”. If yes, its handler goes there. If it touches two — or touches the engine — it goes on the shell. Getting this wrong is how a 4,000-line app.rs becomes a 6,000-line one.
Chapter 12PMK-ch12-

Subscriptions and the zero-idle-CPU rule

Six streams, five of which usually return nothing at all

A subscription in Iced is a stream of events the application opts into. Most apps arm a handful of timers at startup and leave them running. This one arms each stream only while it has work, and the result is a settled window that uses 0.0% CPU — a property the project treats as a release blocker, not a nice-to-have.

12.1 The six streams

StreamArmed whenInterval
Keyboard Always — but iced::event::listen_with returns None for anything the app does not act on, so ordinary typing (handled by the focused editor widget) never spawns a redundant update cycle.event-driven
Toast timeoutui.toast is setfires ToastHide after 3s
Highlight debouncea highlight generation is pending80 ms tick
Autosave polleditor.autosave_pending_since is set 100 ms tick; writes once 400 ms of quiet have passed
Search debouncea query keystroke is pending200 ms tick
Filesystem watchera vault is open notify recursive watch, debounced 300 ms

Animation frames are armed the same way, from motion.is_animating() (Chapter 26).

Why it is like this

The autosave poll (100 ms) is deliberately finer than the autosave debounce (400 ms). A single 400 ms timer would fire on its own phase, not on yours: stop typing 10 ms after a tick and you wait 790 ms for the save. Polling four times as fast bounds the error to 100 ms, at the cost of a few no-op wakeups while you are typing anyway.

12.2 The filesystem watcher

A notify recursive watch on the vault, debounced by VAULT_WATCH_DEBOUNCE = 300ms, emits VaultFilesChanged with the changed paths. External edits — a git pull, a change from another editor — refresh buffers, the file tree and the link index without a restart.

The subtlety is SELF_WRITE_GRACE: a 3-second window during which events caused by the app's own saves are suppressed. Without it, every autosave would bounce straight back as an external change notification, and the app would spend its time reacting to itself.

Trap Adding an always-on timer is a regression even when it looks cheap. “A 1-second tick to refresh the clock” costs a wakeup every second forever, on battery, in every window, and it defeats a property that took deliberate work to establish. If you need periodic work, arm it from the condition that makes it necessary and disarm it the moment that condition clears.

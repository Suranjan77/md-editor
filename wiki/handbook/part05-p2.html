Chapter 5PMK-ch05-

AppState and the lock discipline

Four mutexes, and the rule that keeps them from ever being held long

The whole engine hangs off one struct, shared as an Arc. It is small enough to quote in full, and the interesting part is not what it contains but how long its locks are held.

core/src/state.rs
pub struct AppState {
    pub vault_root: Mutex<Option<PathBuf>>,
    pub file_index: Mutex<FileIndex>,
    pub db: Mutex<Connection>,
    pub pdf_renderer: Option<PdfRenderer>,
}

Three std::sync::Mutex fields and one optional renderer handle. There is no RwLock, no async mutex, and no interior-mutability cleverness — because the design goal is not “fast locks” but short locks.

Two constructors exist. AppState::new() opens the on-disk database; AppState::new_in_memory() opens an in-memory one with no PDF renderer, which is what the test suite uses — that single line is why 56 core tests can run in a container with no display and no filesystem state to clean up.

5.1 The rule: do the slow work before you take the lock

The clearest example is set_vault_root, which runs when you open a vault. It has to walk the entire directory tree, read every markdown file, extract text from every PDF, build a fresh link index, and replace the full-text search table. On a large vault that is seconds of work. If any of it happened while holding db or file_index, the UI would freeze for exactly that long the moment anything else touched the engine.

So the function is deliberately split into phases, and only the last one takes a lock.

Why it is like this A Mutex in Rust is not slow. What is slow is the code you run while holding it. The compiler will happily let you read_to_string inside a guard's scope, and nothing will look wrong in review — the bug shows up only as “the app hangs for two seconds when I open a big vault”, which is exactly the kind of defect that never gets a bug report, only a shrug.
Check yourself

You are adding “count the words in every note in the vault” to the engine. Sketch the shape.

Answer: lock vault_root, clone the PathBuf, drop the guard. Walk and count with no locks held. If you need to store the result, take the db lock only for the write. Three locks, each held for microseconds — and no lock held across a file read.

Chapter 6PMK-ch06-

The database

Eight tables, two pragmas, and a migration strategy that fits in a paragraph

One SQLite file holds every piece of state that is not your content. It is opened once at startup, kept behind the db mutex, and never sharded, replicated, or versioned by hand.

6.1 Two pragmas

PRAGMA journal_mode = WAL;
PRAGMA synchronous  = NORMAL;

Both are applied best-effort at connection time and fall back silently if the platform does not support them. WAL (write-ahead logging) keeps writes fast and, critically, stops a writer from blocking a reader — which matters because the UI reads settings on paths a background task may be writing to. synchronous = NORMAL is the documented pairing with WAL: safe against an application crash, and it does not fsync on every commit.

Note synchronous = NORMAL with WAL is not the same guarantee as the atomic file write in Chapter 8. Your notes are protected by the temp-file-and-rename protocol; the database is protected by WAL. Different mechanisms, because they protect different things: one is your writing, the other is your scroll position.

6.2 The schema

What each table is for

TablePurpose, and the thing that is easy to get wrong
settings Key/value application state. The keys actually written are window_size, last_vault, last_file, scroll:<path>, cursor:<path> and tracker_config. Window position is deliberately not stored — only size.
file_search An FTS5 virtual table over (path, content) holding both markdown text and extracted PDF text, so one query covers both. Rebuilt wholesale inside one transaction when a vault opens — not incrementally.
pdf_documents Known PDFs by content id. When a PDF is copied or restored and its id changes, rows recorded for the same path and the same size are adopted under the new id, so annotations are not orphaned. The size check is what stops a genuinely different file inheriting them.
pdf_annotations The sidecar highlights and notes. ranges_json is character intervals on the page text layer; rects_json is bounding boxes in PDF points (Chapter 19 explains why points and not pixels).
pdf_text_cache Extracted text by vault-relative path, invalidated by size and mtime. Empty results are cached too, so a scanned PDF with no text layer is not re-extracted on every vault open.
pdf_references The resolved cross-reference list per document, stored as (RESOLVER_VERSION, links) so that changing the resolver transparently invalidates every cached result.
tracker_sessions, tracker_kv Logged study sessions, and the curriculum's checkbox and status flags.
tracker_activity Created by the schema, available for an activity feed, and currently written by nothing. Left in deliberately; deleting it would be a migration for no benefit.

6.3 Migrations

Versioning uses SQLite's built-in PRAGMA user_version. There is no migration framework and no migrations/ directory. The whole strategy is two functions:

  • init_schema() runs the full idempotent DDL — every statement is CREATE TABLE IF NOT EXISTS.
  • apply_migrations() runs afterwards and holds the additive steps, each bumping user_version.
Trap Adding a column by editing the base DDL only affects fresh databases. Every existing user keeps the old table and your code starts failing on a column that does not exist. New columns go in apply_migrations(), always — even when you are “sure” nobody has an old database yet, because you have one on your own machine from last week.
Chapter 7PMK-ch07-

Where the database lives

Portable by default, with two fallbacks and one careful migration

Most desktop applications put their state in a per-user configuration directory and never think about it again. MD Editor puts it beside the executable, which is a deliberate and slightly unusual choice with a small amount of machinery behind it.

The goal is that the whole application is one folder: binary, PDFium library, icon, licence, and md_editor_settings.sqlite. Copy that folder to a USB stick and your settings, highlights and study history come with it. That only works if the executable's own directory is writable — which it is for a portable download, and is not for a system install under /usr/bin. Hence a ladder.

Why it is like this Copying rather than moving looks wasteful — you now have two databases. It is the right call anyway: a move that is interrupted halfway (a full disk, a killed process) leaves the user with neither file. A copy that is interrupted leaves the original untouched, and the next launch simply tries again.
Try it Build a release binary, copy it plus libpdfium.so into an empty directory, run it, open a vault, and confirm md_editor_settings.sqlite appears in that directory. Then chmod -w the directory and run again: the database should be created under ~/.local/share/md-editor/ instead. That is the whole ladder, observable in two minutes.
